# Style Mix：把两个画派混成一套网页风格

流派数据在本目录的 `schools.json`，混合规则在 `references/mixing.md`。不要凭记忆描述流派，所有颜色、字体、规则都从数据里取。

两个脚本，都只要 Node 22+，不装依赖：

- `scripts/mix.mjs` 按 mixing.md 把选定的流派算成完整的 DESIGN.md（含代码提示词和生图提示词）。正文和 tasteux.com 工作台导出的一致；另外带 Google Stitch 格式的 YAML 前言（颜色、字体、圆角和组件 token），能通过 `npx @google/design.md lint DESIGN.md`，Stitch、Impeccable 等读 DESIGN.md 的工具可以直接用。生图提示词会去掉题跋、题签、剪报这类会被画成乱码文字的母题。
- `scripts/check.mjs` 在本机 Chrome 里按 DESIGN.md 检查页面，见"验收"。

有 Node 时一律用 mix.mjs，不要手算：

```
node <本目录>/scripts/mix.mjs 包豪斯 野兽派 --subject "a poster for an independent bookstore"
```

- 参数顺序就是主、副：先写管布局的，再写管颜色的。流派可以写中文名、英文名或 id；只写一个就是纯粹形态；第三个只贡献母题。
- `--json` 只输出主副、质感强度、强调色、禁忌、负向词和各强调色上能放什么，适合检查。
- 流派名不存在时脚本报错并列出现有流派。推荐最接近的一个，等用户确认。
- 前言里的 `x-style-mix: "主+副"` 记录组合，check.mjs 和下一轮迭代都靠它认出组合，不要删。

没有 Node 时，完整读一遍 `references/mixing.md` 和 `references/format.md`，按 format.md 的格式手算。

## 先判断是哪种任务

- **出方案**：用户只要风格、DESIGN.md 或提示词。走"流程"第 1–4 步。
- **做新页面**：用户要页面，但项目里还没有按本技能生成的 DESIGN.md。走第 1–5 步。
- **迭代已有网站**：项目里已经有页面，用户要改版或继续改。走"迭代已有网站"。

## 流程

1. **识别流派与定主副**：按 `mixing.md` 第 2 条决定主流派（结构）和副流派（表皮），确定参数顺序。用户说"原样""纯粹""只要 X 风格"时只传 X。
2. **生成**：运行 `mix.mjs`。脚本在展签下写出它做的替换（比如两个都是表皮流派时改用极简主义做结构），原样保留。
3. **补上需要判断的部分**：
   - 主张：脚本给的是一句模板，可以改写成更具体的一句，说清骨架和表皮各来自哪里；不要写"融合了 A 与 B 的精髓"这类空话。
   - 主视觉：表皮流派有公有领域原作（DESIGN.md 的"原作"一节）时优先用原作，按那一节的规则放图和写图注；只有没有合适的原作时才用生图提示词。
   - 生图主题：用户没给时，按场景写一个具体画面（比如落地页就写这个产品的主视觉），替换 `{主题}`；不要写 "beautiful artwork" 这种空主题，不写艺术家名字，也不要照着某幅名作的构图写（提示词已经要求原创构图）。
   - 用户要求偏离数据时（比如"包豪斯但要圆角"），照做，并在展签下面用一句话写出偏离了哪条规则。
4. **输出**：依次给出展签、DESIGN.md、写代码用的提示词、生图用的提示词。用户只要其中一部分时，只给那一部分。
5. **做页面**（只在用户要求时）：把 DESIGN.md 存进项目根目录，它就是唯一的设计依据。用用户项目现有的技术栈实现；没有项目时写一个没有依赖的单文件 HTML。做完按"验收"检查。

## 迭代已有网站

同一个网站会被反复改，每一轮都以项目里的 DESIGN.md 为准，不要每轮重新发明风格。

1. **读现状**：先找项目根目录的 `DESIGN.md`。
   - 前言有 `x-style-mix: "主+副"`（旧版是第一行的 `<!-- style-mix: 主+副 -->`）的，就是本技能生成的。先读"适用范围"和"迭代记录"。再把 `mix.mjs` 的新输出写到临时文件里比较，数据有更新时，除"适用范围"和"迭代记录"两节外以新输出为准，并告诉用户变了什么。
   - 没有 DESIGN.md 时，读页面现有的 CSS 变量、字体和布局，告诉用户它最接近哪个组合。很多网站的外壳（导航、章节、按钮）和展品（作品、截图、别的风格的预览）不是一套风格，先和用户确认 DESIGN.md 只管哪部分。用户确认后生成 DESIGN.md 存进项目根目录：在"适用范围"里写明它管哪部分，不管的区域写成 `检查时排除：` 一行；把页面现有的、和规则不一致的地方（比如衬线标题、2px 圆角）作为第一条迭代记录的"偏离的规则"列出来，等用户决定保留还是改，不要直接改回规则。
   - **列出页面模板**：多页面网站先列出所有页面模板（首页、文章页、列表页、隐私页、各语言版本……），每个模板记一个示例网址，在"适用范围"里逐个写明管不管。和首页共用一套外壳样式（同一个 CSS、同一套导航和页脚）的页面默认算管：只改首页会让它们悄悄留在旧风格，check.mjs 对它们多半只报 WARN，不会拦住。不管的页面写明原因，并在迭代记录里记成待办。新增页面模板时也补进这份清单。
2. **定这一轮的范围**：一轮只做一件事，并在开工前说清楚：
   - **换组合**：换主流派会改布局、字体、圆角、动效；换副流派只改颜色、质感、母题和主视觉。先说清会变什么、不会变什么，再动手。
   - **按规则修**：组合不变，把页面里违反 DESIGN.md 的地方改掉（硬编码颜色、多出来的强调色、被禁止的阴影或圆角、压在正文上的质感）。
   - **改一个区块**：只动用户点名的区块，其他区块不动。
   - 换组合或按规则修时，范围是"适用范围"里所有标为管的页面模板，不只首页。
3. **保留不属于风格的东西**：文案、链接和 URL、`<title>`、meta description、canonical、Open Graph、JSON-LD、`lang`、标题层级、表单、统计和广告代码，除非用户要求，都不改。颜色和字体只通过 DESIGN.md 里的 CSS 变量进入页面，不在组件里写死色值。
4. **验收**：见下一节。
5. **记录**：在 DESIGN.md 末尾"## 迭代记录"的表格里加一行，格式固定为 `| 日期 | 这一轮 | 偏离的规则 |`，没有偏离写"无"，偏离写成"规则 → 现在的做法（用户确认 / 待确认）"。有意新增或修改的标题、链接、meta 也写进"这一轮"一列（比如"新增 H3「一行安装」、2 个下载链接"），再重新 `--save-baseline`。下一轮先读这一节，不要把用户确认过的偏离改回去；对应的检查项在验收时用 `--allow` 跳过。

## 验收

页面做完或改完，都要真的打开看，不要只读代码就说完成。

1. **跑检查**：页面能在浏览器打开（本地预览地址或 HTML 文件）时运行

   ```
   node <本目录>/scripts/check.mjs http://localhost:3000/ [更多页面的网址...] --design DESIGN.md --shot "#hero"
   ```

   它在 1440px 和 390px 下截图，并检查：文字对比度（按实际底色算）、圆角、阴影、渐变文字、玻璃效果、多出来的强调色和调色板外的颜色、标题和正文字体、横向溢出、手机上的点按尺寸、`lang` / `title` / h1 / 图片 alt、原作（`[data-original]` 不能加滤镜和半透明，图注要链接出处）、Tab 焦点环、减少动态效果时还在跑的动画。第一行是 `CHECK: PASS` 或 `CHECK: FAIL`，有 FAIL 时退出码为 1。
   - `--shot 选择器`（可重复）截这一轮改动的区块。截图前脚本会把懒加载的图片全部加载完；加载失败的图片会报 images FAIL，所以截图里空白的图就是真的坏了。截图放在 `.style-mix/check/`，不要提交进仓库。
   - 多页面网站把"适用范围"里标为管的每个页面模板的示例网址一起传进去（`check.mjs http://localhost:3000/ http://localhost:3000/guide/ http://localhost:3000/en/ ...`），一次出一个结论；每页的截图在各自的子目录里。只查首页不算验收。
   - 迭代已有网站时，动手前先对这些页面跑一次 `--save-baseline .style-mix/baseline.json`，改完用 `--baseline .style-mix/baseline.json` 再跑：标题、meta、canonical、JSON-LD、h1–h3、链接、脚本（统计和广告）、iframe、表单有任何变化都会报 FAIL。脚本和 iframe 只比页面 HTML 原文里写的，广告运行时插入的 iframe 和子脚本不算。基线按页面路径分开存在这一个文件里（换域名或端口不影响），`--save-baseline` 只覆盖这次查的页面。这一轮新增的页面不在基线里，只报 WARN；确认内容后单独对它跑一次 `--save-baseline` 加进去。
   - 用户确认过的偏离用 `--allow radius,shadow` 这类参数跳过对应检查，并写进迭代记录。DESIGN.md 里"检查时排除："列出的区域自动不查，也可以用 `--ignore 选择器` 临时排除。
   - 没有 Chrome 或页面打不开时，按 `references/format.md` 末尾的清单手查，并说明没能自动检查。
2. **看截图**：逐张看两个宽度的首屏（`*-fold.png`）和 `--shot` 的区块图。`*-overview-*.png` 是缩小的整页分段，只用来看有没有布局断裂。质感浓淡、母题用得对不对、整体像不像这个组合，脚本判断不了，要靠眼睛。
3. **输出结果**：把 `CHECK:` 那一行、每条 FAIL 和你目测的结论作为最后一部分输出。未通过的先修，修完重新检查，最多三轮；还有未通过的，如实列出。WARN 逐条看，不合理的说明原因后可以保留。

## 规则

- 不往调色板里加新颜色，也不改颜色值。数据里的配色都过了对比度校验。
- 不给一个流派造它没有的结构。表皮流派（`roles` 里只有 `surface`）不能决定布局。
- 页面需要深色区块时，只能做反相：`--ink` 当底、`--bg` 当字，按"无障碍"里算好的对比度，不另造深色。
- 中文大标题按"字体"里的写法处理，不用 font-stretch、scaleX 或伪斜体去模仿拉丁字母的窄体和斜体。
- 质感用 `references/textures.css`，不要自己另写一套。
- 一次最多混合两个流派。用户给三个时，前两个做主副，第三个只贡献母题，并说明这么做的原因。
- 生图提示词用英文，因为生图模型对英文更稳定；页面 UI 文案和其他输出用用户的语言。
